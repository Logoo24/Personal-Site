# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Logan Randall's personal site — a **static HTML/CSS/JS site** (no framework, no bundler). Vanilla JS, GSAP loaded from CDN, and a small Node build step that compiles markdown blog posts. Deployed via Vercel (`vercel.json`), with `/api/*` as Vercel serverless functions for the CMS auth flow.

> Note: `SETUP.md` describes a Cloudflare Pages + Cloudflare Worker setup. The actual current configuration is Vercel + Vercel serverless functions (`api/auth.js`, `api/callback.js`, `vercel.json`). When something disagrees, trust the code, not `SETUP.md`.

## Commands

```bash
npm install          # one-time
npm run build        # runs build.js — required after any change to _posts/ or post-template.html
npm run resume-pdf   # re-renders files/logan-randall-resume.pdf from _src/resume-pdf.html (needs local Chrome/Edge)
```

There are no tests and no linter. To preview locally, run a static file server from the repo root (`.claude/launch.json` runs `.claude/serve.js` on port 8123, which mirrors `cleanUrls` and the `vercel.json` redirects and also runs the family hub locally — see below; it listens on 127.0.0.1 only, answers only a localhost `Host`, and never serves dot-files or `node_modules`, so `.env.local` can't leak to the network); opening `index.html` straight from disk mostly works but root-relative paths like `/images/...` won't resolve. The build modifies `index.html`, `blog.html`, every page's OG block, and `sitemap.xml` **in place** — running it during a working session will show up in `git diff`.

## Build pipeline (`build.js`)

`npm run build` does these things:

1. For each `_posts/*.md` (skipping `draft: true`): parses frontmatter with `gray-matter`, renders markdown with `marked`, substitutes `{{key}}` placeholders into `_src/post-template.html`, writes to `posts/<slug>.html`.
2. Rewrites the post list inside `blog.html` between the literal HTML comments `<!-- POSTS_START -->` and `<!-- POSTS_END -->`. **Personal posts only** — class posts live on their class page (see "Classes" below). With no personal posts it writes an empty-state message linking to the class pages.
3. Rewrites the top-3 recent **personal** posts inside `index.html` between `<!-- RECENT_POSTS_START -->` and `<!-- RECENT_POSTS_END -->` (falls back to links to the class pages when there are none).
3b. Writes one page per class, `classes/<slug>.html`, from `_src/class-template.html` (deletes pages for classes no longer in the list), and fills the nav's Blog dropdown on every page (root pages, `404.html` with root-absolute links, `posts/*`, `classes/*`) between `<!-- BLOG_MENU_START -->` / `<!-- BLOG_MENU_END -->`.
4. Writes the homepage stats via `setStat()`, which rewrites the `<div data-stat="…" data-count="N">N</div>` elements in `index.html`: projects shipped (count of `.proj` cards in `projects.html`), blog posts, and academic posts.
5. Injects `<meta og:image>` / `<meta twitter:image>` tags into every page (including each generated post) between `<!-- OG_IMAGE_START -->` and `<!-- OG_IMAGE_END -->` markers. The URL is `SITE_URL` + `OG_IMAGE` (both constants in `build.js`; currently `/images/og-card.jpg`, a 1200×630 JPG). Social crawlers don't run JS, so these tags **have to** be baked in at build time — and the image must be PNG/JPG, since most crawlers ignore SVG.
6. Generates `sitemap.xml` at the repo root listing every static page + every blog post (with publish date as `lastmod`), using clean URLs (`/about`, `/posts/<slug>`) since `vercel.json` has `cleanUrls: true`. `robots.txt` references the sitemap so crawlers find it.

Template values (title, summary, dates…) are HTML-escaped when substituted into `post-template.html`; only `{{body}}` (the rendered markdown) goes in raw.

**Do not remove those marker comments** — `injectBetween()` silently skips the file if the markers aren't found. If you change the post-card markup, change it inside `build.js` (the strings that get injected), not just in `blog.html` (it'll be overwritten on next build).

Slug = filename minus `.md`, lowercased, non-`[a-z0-9-]` replaced with `-`. Dates are parsed at UTC noon to avoid timezone shifts.

## Content architecture

**Everything except blog posts is hard-coded HTML.** To change wording on the homepage, About, Projects, or Resume, edit the HTML file directly — there is no JSON/CMS layer for page content any more (it was removed deliberately; don't reintroduce it).

**Blog posts** — markdown in `_posts/`, rendered at build time into `posts/*.html`. This is the only content managed through the CMS (`/family/manage`). Frontmatter shape:

```yaml
---
title: "..."
date: 2026-06-15
postTo:                           # where it goes: the CMS's "Post to" choice
  type: personal                  # or a class's slug, e.g. hum-202
  section: essays                 # only for a class whose page has sections (HUM 202)
summary: "..."
readMinutes: 5
draft: false
inProgress: false                 # optional: true = page is built, but left out of post lists, homepage stats and the sitemap
---
```

A post without `postTo` still works the old way, with `category: personal | academic` plus `course: "MKT 353"` for class posts; `build.js` `CATEGORY_LABELS` also accepts the legacy category values `essay`/`class`/`research`/`project` (`academic`/`class`/`research` all count as class posts). Every post in the repo uses `postTo` now.

**Images in posts**: a markdown image's *title* sets its placement — `![alt](/images/uploads/x.webp "left")`, `"right"` or `"center"` (default), optionally with a caption after a colon (`"right: My caption"`; a title with no position word is just a caption). `build.js` (`marked.use` image renderer + `renderMarkdown()`) turns each into `<figure class="post-img post-img--left|right|center">` and lifts it out of its `<p>`; styles are under `.post-img` in `styles.css` (left/right float with text wrapping, un-floated under 560px; headings clear floats). CMS uploads go to `images/uploads/` and are downscaled to WebP on upload (`media_libraries` in `family/manage/config.yml`).

**Classes**: the class list is `_data/classes.json` (`{ classes: [{ code, name, archived }] }`), editable from the CMS → Classes. Slug = `code` lowercased with non-alphanumerics → `-` (`MKT 353` → `mkt-353`), so changing a class's code changes its URL. A post's `postTo.type` names its class by slug (older posts: `course`, matched by slug); a class not in the list gets a page anyway (build warns), and an old-style academic post with no `course` goes under "Other classes". `archived: true` moves a class from "Classes" to "Past classes" in the Blog dropdown and labels its page "Past class" — the page and its posts stay live. Class posts' "back" button links to their class page instead of `blog.html`. A class can have its own layout, `_src/class-<slug>.html`, used in place of `class-template.html`; it can show any post's details with `{{post:<slug>:<field>}}` (`href`, `title`, `summary`, `readMinutes`, `image`/`imageAlt` = the post's first picture), and the build warns if a slug doesn't exist. `{{#unplaced section="<id>" label="<CMS label>" default}}…{{/unplaced}}` blocks in such a layout are filled with the class's finished posts that no `{{post:<slug>:…}}` names (oldest first): the block is repeated per post, with `{{post:*:<field>}}` standing for it, and a post with no picture loses the block's `{{post:*:image}}` `<img>`. Each post goes to the block whose `section` matches its `postTo.section`, else to the `default` block (else the last). The blocks' `section`/`label` are also what the CMS offers as that class's Section choice (see CMS below). The build logs what it auto-placed (and where), and warns about unplaced posts when a custom layout has no such block. HUM 202 uses this for its graded portfolio hub (`_src/class-hum-202.html`, styles in `css/hum-202.css`): three hand-placed sections of image cards, each ending in an unplaced block (`early-modern`, `19th-century`, `essays` = default), so a new post appears in whichever section was picked in the CMS. A post with a hand-placed card stays where that card is, whatever its section says. Its two 19th Century pages are `inProgress` placeholders.

**Blog dropdown** (`li.nav-dd` in every page's nav, including `_src/post-template.html`, `_src/class-template.html` and `404.html`): the "Blog" word is a normal link to `blog.html`; the chevron `button.nav-dd-toggle` toggles `.open` (wired in `main.js`), and on desktop hovering also opens it (CSS). In the mobile full-screen menu the list opens inline under Blog. Any new page with a nav needs the same `li.nav-dd` block with the BLOG_MENU markers, and `build.js` must know about it (`ROOT_PAGES`).

**Projects** appear in two independent places: the homepage "Selected work" grid (`index.html`, plain `.card`s) and the full list on `projects.html`. On the projects page each project is a `.card.proj-card` inside a `.proj.proj--<name>` wrapper in a 2-column `.proj-grid`. A project with a custom look gets styles under `.proj--<name>` in `css/projects.css`, and can put decoration in a `.proj-behind` div that renders under the card (z-index 0) — that's how the ChooseAMovie popcorn bucket peeks over the card's top edge. Linked cards are `<a class="card proj-card">`; external links use `target="_blank" rel="noopener"` and a `↗` in the corner label. The ChooseAMovie card hotlinks its logo from `https://www.chooseamovie.app/brand/logo-lockup.svg` and falls back to a text wordmark via an inline `onerror`.

**Images**: the homepage hero is `images/logan-hero-720.webp` / `-1040.webp` (via `srcset`), generated from the original full-res cutout `images/logan-hero-cutout.svg` (which is just two embedded PNGs: photo + luminance mask; it's 4 MB, so never reference it from a page). The About page uses `images/about-logan-marisa.jpg` (hero, 4:5 crop) and `images/about-wedding-day.jpg` (inline `.figure`); the Resume headshot is `images/logan-headshot.webp` (a 694×694 square, cropped to 4:5 by CSS). There's no image tooling in `package.json` — photos were resized with Windows' System.Drawing, and project screenshots captured with headless Chrome.

**Social links** (LinkedIn, Instagram, Facebook, email) are a `ul.socials` list duplicated in `about.html` and `resume.html` — keep the two in sync. On print, the resume's social links show their full URLs.

**Resume** exists in two forms that must be kept in step: `resume.html` (the "story" version — a timeline of `.tl-item` entries with logo badges, metric tiles and optional `figure.tl-media` photos; styles under `RESUME TIMELINE` in `styles.css`) and the one-page PDF `files/logan-randall-resume.pdf`, rendered from `_src/resume-pdf.html` by `npm run resume-pdf` (not part of the Vercel build — the PDF is committed). The PDF deliberately omits Logan's phone number; never add it back. After regenerating, check it's still one page.

## CMS (`/family/manage`)

Sveltia CMS (a Decap-compatible drop-in, loaded in `family/manage/index.html` from unpkg, pinned to an exact version: to update, pick a release that's been out a couple of weeks) configured in `family/manage/config.yml` (linked by absolute URL via `rel="cms-config-url"`, since `/family/manage` has no trailing slash). It sits behind the family hub sign-in and is admin-only: `middleware.js` sends anyone whose Google email isn't in `FAMILY_ADMIN_EMAILS` back to `/family` (password sign-ins never count, having no verified email), and the hub home page hides its card for them (`isAdmin()` in `api/_family/session.js`; the list is an env var because the repo is public). It then asks for its own GitHub sign-in to commit. `/admin` redirects here (`vercel.json`). Two collections: blog posts in `_posts/`, and "Classes" (a file collection editing `_data/classes.json`). Where a post goes is one "Post to" field (`postTo`), a variable-type object (`types`): Sveltia has no "show this field when…" option, and picking a type showing only that type's fields is its one way to hide what doesn't apply. The types are Personal blog plus one per class (current first, then "(past class)"), and a class whose layout has `{{#unplaced section=…}}` blocks brings a required Section select (radio buttons). `build.js` (`writeCmsPostTo()`) writes those types into `config.yml` between `# POST_TO_TYPES_START` / `# POST_TO_TYPES_END` on every build, from `_data/classes.json` and the class layouts, so don't hand-edit between the markers; Vercel builds before it deploys, so a class added in the CMS shows up under Post to once the deploy is live (reload the manager). If you add a frontmatter field that the build uses, add it to the posts collection too. To try a config change without GitHub, Sveltia's `test-repo` backend runs entirely in the browser: a page with the Sveltia script, a `cms-config-url` link to a copy of the config with `backend: { name: test-repo }`, and a `<link rel="cms-seed-url">` to a `{ "files": [...] }` manifest seeds it with real posts (saved files live in the browser's origin-private storage, `sveltia-cms-test`).

Auth flow (Vercel serverless, in `api/`): Sveltia's "Sign in with GitHub" opens `api/auth` in a pop-up, which hands a GitHub token back with the Decap-style `postMessage` handshake (`api/_family/cms-auth.js`, posting only to the site's own origin).
- `api/auth.js` — if the visitor has a family-hub session from an admin Google email (`isAdmin()`) and `GITHUB_CMS_TOKEN` is set, it returns that token immediately: no GitHub page. `GITHUB_CMS_TOKEN` is a fine-grained personal access token limited to this repo with Contents read/write, so commits are made as its owner. Otherwise it redirects to GitHub's OAuth authorize URL (scope `public_repo`, enough for a public repo; a random `state` kept in a 10-minute `cms_oauth_state` cookie).
- `api/callback.js` — checks that `state` against the cookie, exchanges GitHub's code for a token and hands it back the same way.
- Requires env vars `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` in Vercel for the OAuth fallback; `GITHUB_CMS_TOKEN` for the instant admin sign-in.
- `family/manage/config.yml`'s `base_url` and `auth_endpoint: api/auth` must match the deployed domain.

## Family hub (`/family`)

A private area for the Randall family, separate from the public site. Every footer's "Sign in" links to `/family`.

- **Sign-in**: `middleware.js` (Vercel Routing Middleware) sends anyone without a valid `fh_session` cookie to `/family/login` (`/family/login` and `/family/assets/*` are open). The cookie is an HMAC-signed token (`api/_family/session.js`, Web Crypto only so it runs in both the Edge middleware and the Node function). Two ways in: the family password (`FAMILY_PASSWORD`, plus a typed name) or Google (Google Identity Services button → ID token verified server-side; the email must be in `FAMILY_GOOGLE_EMAILS`). **Never commit the password** — the repo is public.
- **API**: one function, `api/family.js`, routed by `?r=` (one function keeps the Hobby plan's function count down). Helpers live in `api/_family/` (underscore = not deployed as functions). Non-GET requests must send `x-family-hub: 1` (CSRF guard); the hub's `Hub.api()` does.
- **Storage**: a private Vercel Blob store — `recipes/index.json` (summaries; written with ETag `ifMatch` retries), `recipes/<id>.json`, `media/<random>.<ext>` (served through `?r=media` to signed-in family; a public recipe's own photos are also served on its link), `shared/slugs.json` (public links). ETags for those conditional writes come from `head()`, not `get()`: the CDN's etag never matches what `put()`'s `ifMatch` checks. Without a Blob token and off Vercel, `api/_family/store.js` falls back to a gitignored `.family-data/` folder.
- **Pages**: plain HTML under `family/` sharing `family/assets/hub.css` + `hub.js` (`window.Hub`: API, header/user menu, theme, toasts, markdown with the same image-placement rules as `build.js`, recipe rendering, photo downscaling). Each page has `<header class="hub-bar" data-crumbs=...>` and calls `Hub.ready()`. Pages load `/css/styles.css` for tokens; note its global `section` padding is reset for the hub. To add a tool: a page at `family/<slug>.html` (or folder), a card in `family/index.html`, and a `.hub-app--<slug>` tint in `hub.css`.
- **Cookbook** (`family/cookbook/`): list/search/tags, `recipe?id=` (scaler, tap-to-check, keep-screen-on, print), `edit` (paste-a-list ingredient parser, story markdown with photo upload, a tag picker — chips plus a search list with "Want to make" first, then tags by how many recipes use them, and an "Add new category" option — and a notes box that's a "- " bullet list by default, Enter adding the next bullet; text boxes marked `data-grow` get taller as you type (title and description are `data-single` one-line textareas that wrap but ignore Enter), re-fitting on width changes via a ResizeObserver and again once the web font loads; on new recipes, a sparkle "fill in from a link, pasted text, or a photo or file" box). Tags always start with a capital letter, enforced in the picker and again in `normalize()` (`api/_family/recipes.js`). Notes render with every line kept on its own line (`Hub.notesMd()` / `notesMarkdown()` in `share-page.js`: marked's `breaks`, plus a blank line slipped in after a bullet so a plain line doesn't join it). In the recipe view, the Steps styles and tap-to-check are scoped to `.rc-steps > ol > li`, because the Notes box sits inside the Steps section, `print` (whole cookbook or `?ids=` → browser "Save as PDF"). Quantities parse/scale/format via `js/recipe-scale.js`, shared by the hub, `build.js` and `main.js`.
- **Recipe formatting**: steps, notes and the story stay plain markdown text — `**bold**`, `*italic*`, `- ` and `1. ` lists, and colored words written `[words]{red}` (red/orange/green/blue/purple/highlight; `.tx-*` classes in `styles.css`). `js/recipe-text.js` (shared by `hub.js` and `share-page.js`, like recipe-scale) holds the marked color extension, the notes line rules (`notesSource()`, which also unwraps old `- 1.` lines: the notes box used to bullet every line, so typed numbers became lists nested in bullets), `stepSource()` (steps get inline formatting only, with `<`/`>` escaped), `plain()` (marks stripped, for schema.org) and `safeRenderer` (marked `html` and `link` overrides: raw HTML shows as text, and links go only to http(s), mailto or relative URLs, since marked lets `javascript:` through). Both marked setups use `safeRenderer`; recipe text is written by anyone with the family password, so it must never carry a script. The editor's `.ed-toolbar`s (story, notes, and one over the steps that acts on the step box last tapped) insert that syntax; bold/italic/color toggle. Websites can't add buttons to iOS's tap menu, and its own B/I/U only appears in rich-text editors, so the toolbar is on the page.
- **Shopping list** (recipe page, `shoppingDialog()` in `recipe.html`): ticks the scaled ingredients (`Hub.shoppingItems()`), then "Copy list" (pasting several lines into Reminders makes one reminder each) or, on Apple devices, "Add to Reminders", which opens `shortcuts://run-shortcut?name=Add to Shopping List&input=text&text=…`. Pages can't reach Reminders directly, so each device needs that one-time Shortcut (Split Text by New Lines → Repeat with Each → Add New Reminder); the setup steps are in the dialog, and `SHORTCUT_LINK` can hold an iCloud link to a ready-made copy.
- **Making a recipe public** (`api/_family/share.js`) gives it an unlisted link, `/recipes/<slug>` (slug from the title; editable from the recipe page's "Link options" pop-up). Nothing is committed or rebuilt: `shared/slugs.json` in Blob maps slug → recipe id, and `vercel.json` rewrites `/recipes/:slug` (and `/recipes/:slug/photos/:file`) to `api/recipe.js`, which renders the page live from the cookbook (`api/_family/share-page.js`: site recipe-card styles + `main.js` scaler, Open Graph tags for link previews, `noindex`, and a corner link: "Back to loganbrandall.com" for guests, "Back to the family cookbook" for anyone signed in to the hub). So it's live instantly, always current, and off the moment it's made private. Only photos the recipe uses are served. The page carries a strict Content-Security-Policy (`SHARE_CSP` in `share-page.js`: the site's own scripts plus a hash of the theme line, which `THEME_SCRIPT` holds), so any new inline script there needs its hash added. Public lookups cache the slug map in memory for 30 seconds (`slugMap()`), so made-up links can't use up Blob reads; privacy still applies at once because the recipe's own `published` field is checked every time. Public recipes are deliberately **not** on the main site — no listing page, Blog dropdown entry, homepage stat or sitemap entry. The hub's share button uses the Web Share API (the phone's share sheet), falling back to copying the link.
- **"Want to make"** is a special tag (`Hub.WANT_TAG` / `Hub.isWant()` in `hub.js`) for recipes the family hasn't tried yet. They're left out of the cookbook's All list, the other tag chips, search, the hub home page and the whole-cookbook PDF, and only show under their own chip. A to-try recipe's page has a "We made it! Add to cookbook" button that removes the tag.
- **Calendar** (`family/calendar.html`): the page draws its own month grid/agenda from `GET calendar`. With `GOOGLE_CALENDAR_SERVICE_ACCOUNT` set (a service account's JSON key; the family calendar shared with its email, "Make changes to events"), `api/_family/gcal.js` reads and writes through the Calendar API (JWT signed with `node:crypto`, no Google SDK), and any signed-in family member can add, edit and delete events (Add event button, Edit/Delete in the day drawer; repeating events offer "This event"/"All events"; simple Daily/Weekly/Monthly/Yearly repeats, anything fancier is kept as is). Times are entered in the device's own time zone and sent with it. Without the key, `api/_family/calendar.js` falls back to the calendar's public iCal feed (read-only, cached 5 min; RRULEs expanded in wall-clock time so events keep their local time across DST) and the editing UI stays hidden.
- **Recipe import** (`POST import`, `api/_family/import.js`): pasting a link (or a whole recipe's text) into the editor's sparkle box returns a draft that fills the form — nothing is saved except the cover photo, which goes to Blob like any upload. The server fetches the page itself (honest bot User-Agent — recipe sites 403 a fake browser UA from Node; private/localhost addresses are refused on every redirect hop), reads its schema.org Recipe JSON-LD, and with `ANTHROPIC_API_KEY` set sends that plus the page text to Claude (`claude-opus-5-5`, structured JSON output) to fill every field including notes/tips and to skip the blogger's story. Instagram posts are read from the post's `/embed/captioned/` page, which carries the caption. The box's "Photo or file" button (or dropping files on the box, or pasting a screenshot into it) sends up to 6 files as `{ files: [{ name, data }] }` (base64): photos of a recipe card or cookbook page, PDFs, `.docx`, and text/Markdown/RTF/HTML files. The page shrinks photos to 2000px first (`Hub.downscale`); a request can't pass 4.5 MB on Vercel and base64 adds a third, so a PDF over ~3 MB is sent as JPEGs of its first pages, drawn with pdf.js (same pinned cdnjs version as Documents). The server goes by each file's bytes, not its name (`sniff()`): photos and PDFs go to Claude as image/document blocks at effort medium (the prompt asks for "(?)" after handwriting it can't make out), `.docx` text is pulled out of the zip with `node:zlib` (`docxText()`), and old `.doc` and HEIC files are refused with a how-to. Nothing from an upload is stored. The Claude call is cut off at 52 s (`CLAUDE_MS`) so a slow read ends in a clear message rather than the function timing out. Without the key, only JSON-LD pages import (no notes), and Instagram, pasted text and files are refused with a "not set up" message. `vercel.json` gives `api/family.js` a 60s `maxDuration` for this.
- **Finance** (`family/finance/`): a money dashboard for Logan and Marisa only. Who can open it:
  - `canSeeFinance()` in `session.js` allows only Google sign-ins on `FAMILY_FINANCE_EMAILS`; password sign-ins never count.
  - It's checked in `middleware.js` (a `FINANCE_ONLY` redirect to `/family`), in `api/family.js` (every `?r=fin-*` route answers 403 to anyone else), and in the `session` route's `finance` flag, which shows the hub card.

  Storage and routes:
  - Routes live in `api/_family/finance/index.js`; the data model is in `data.js`.
  - Every Blob file under `finance/` is AES-256-GCM-encrypted with `FINANCE_ENCRYPTION_KEY` (`vault.js`, with the path as authenticated data). Use `readSecure`/`writeSecure`/`updateSecure`, never `readJSON` directly. `updateSecure` skips the write when nothing changed.
  - Read-only paths pass `{ etag: false }` (store.js `readJSON` option) to skip the extra `head()` call. Blob's Hobby limits (2,000 puts and 10,000 reads a month, shared with the cookbook) are the constraint to design around.
  - Amounts are integer cents. Account balances are positive, and `side` (asset/liability) gives the sign.
  - An account with `private: true` belongs to `owner` (an email), and `visibleAccounts()` hides it, and its snapshot balances, from the other spouse. Ticking "Only me" always makes the account the ticker's own, so it's refused on an account in the other person's name (the same for credit scores).
  - Anything tied to an account the viewer can't see, or to a deleted one, stays hidden: recurring items (`visibleRecurring`), goals (`visibleGoals`), holdings and the securities they name. `deleteAccount` also drops its recurring items and goals, and the recurring scan skips a deleted account's leftover transactions and keys an "Only me" account's series by its owner (`payee~email`), so it never merges with a shared one. A new "always" rule only re-sorts accounts its maker can see.

  Accounts and history:
  - `accounts.js` adds, edits and deletes accounts. Hand-kept accounts can change everything; linked (`src: 'plaid'`) ones only their settings. Deleting an account also removes it from the snapshots.
  - `snapshots.js` keeps per-account balances: daily for 400 days, plus month-ends. Today's snapshot comes from the daily cron and from any visit where balances changed. Past month-ends typed into the Accounts tab's "Edit past months" grid (`applyBackfill`) are listed in that month's `est` array, so the graph dashes them.
  - Days are the family's, not the server's: `familyDay()`, using `FAMILY_TIMEZONE`, default `America/Boise`.
  - Routes that change something answer with a fresh summary (`Fin.save()` on the page), so there's one request per change.

  Banks (Plaid):
  - `plaid.js` is the REST client: plain `fetch`, the `PLAID-CLIENT-ID`/`PLAID-SECRET` headers, `PLAID_ENV` sandbox or production. It logs Plaid error codes only, never tokens or amounts.
  - `sync.js` links a bank (`linkBank`), syncs (`syncAll`), handles `reconnected` (update mode) and removes a bank (`removeBank`, which turns its accounts into hand-kept ones).
  - The Trial plan allows 10 Items ever. `state.itemsUsed` never goes down, and the UI pushes Reconnect over remove-and-relink.
  - Access tokens and `/transactions/sync` cursors live in `finance/secrets.json`.
  - A sync fetches every Item in parallel, then merges in one pass:
    - accounts, plus card and loan APR, minimum payment and due date from `/liabilities/get`;
    - transactions into their month files. Plaid's sign is flipped: money out is negative here. The family's edits survive "modified" updates, and they carry over when a pending charge posts (`pending_transaction_id`).
    - transfer pairing, then holdings into `finance/holdings.json`, then cursors, then today's snapshot.
  - Once an Item reports `HISTORICAL_UPDATE_COMPLETE`, `rebuildFromHistory` fills empty past month-ends for its cash and card accounts, and carries investment balances back 12 months. Both are marked estimated.
  - Opening Finance after 6 hours without a sync triggers one; manual "Refresh now" is throttled to every 10 minutes.
  - `oauth.html` finishes Link for banks that bounce phones out to their own app (`PLAID_REDIRECT_URI` must point at `/family/finance/oauth`).

  Transactions:
  - Stored as `finance/tx/YYYY-MM.json` (`transactions.js`).
  - A category's `kind` decides whether a transaction is income, spending or a transfer. Transfers are left out of totals: `detectTransfers` pairs equal and opposite amounts between our own accounts within 3 days. Loan and mortgage payments stay as spending.
  - `categorize.js` picks a category in this order: the family's rules, then what the family said about that merchant before (`state.payees` entries with `src: 'user'`, `taught()`), then known subscription brands, then Plaid's `personal_finance_category` (unless its confidence is LOW/UNKNOWN), then Claude's earlier answer, then keywords.
  - Picking a category, or "Looks right" / Done on one waiting for review, teaches `state.payees` (keyed by `payeeKey()` of the raw text), even when Plaid picked it (`editTransactions()`). That merchant's other transactions still waiting for review (last 3 months) are sorted the same way at once (`catSrc: 'learned'`; the count comes back as `sortedToo` for the toast). Payment apps and checks (`isGeneric()`: Venmo, Zelle, PayPal, checks…) are remembered but still land in review, since one name covers many things.
  - Whatever's left goes to Claude in one batch: merchant text and in/out only, plus up to 60 of the family's own choices as examples. Answers are remembered in `state.payees` (a merchant already there isn't asked again) and land in the "Needs review" queue (`reviewed: false`).

  - CSV export guards against spreadsheet formulas.

  Recurring (`recurring.js`):
  - `scanRecurring()` reads the last 14 months and groups transactions by direction and merchant: `seriesKey()`, the raw statement text minus any word with a digit in it and banking words, so a reference code that changes every month still matches. "Only me" accounts are keyed by owner. Each item has one of three shapes (`pattern`):
    - `fixed`: subscriptions and fixed bills, the same price (±2¢, or 0.25% on big amounts) at a strict rhythm on a steady day of the month. Charges are grouped by price within a merchant, so Apple's $2.99 and $10.99 are two items.
      - A series that stops and carries on one period later at a new price is the same item, with a `priceChange` and `prices` history.
      - `priceAlert` shows on Recurring and the Overview, and counts in the badge, for 90 days or until "Got it" (`price-ok`, which stores `priceSeen`).
      - Everyday categories (`EVERYDAY`: groceries, dining, shopping, transport) need 4+ charges and never chain price changes.
      - `kind` is `bill` for `BILL_CATS`, otherwise `subscription`.
    - `month`: bills that change (rent paid in parts, power, phone), as the merchant's total per month. Only for `BILL_CATS` (housing, utilities, insurance, loans, kids, education), paid in 3+ of the last 6 full months.
      - `amount` is the average of the last 3 months; `low`/`high` come from months paid in the usual number of `parts`.
      - `days` is each part's median day; `thisMonth`/`thisMonthCount` are what's paid so far.
      - `monthDue()` spreads what's left of this month over the usual days still to come (one "late" line if they've passed).
    - `varies`: income (paychecks, interest) and bills that come every 2 or 3 months: a rhythm, with amounts that may move.
  - Merging into `state.recurring` matches last scan's items by shared transactions (`txIds`), then by `key`, so a price change keeps the id. Items from before this version match by their old payee key; unmatched old ones are dropped. Confirmed or dismissed items that stop being found are kept, marked ended.
  - The family's choices survive rescans: `status` (`detected` | `confirmed` | `ignored` | `canceled` | `manual`), plus `canceledOn`, `customName`, `customAmount`, `customCadence`, `person`, `note`, `priceSeen` and `pinned`.
  - Canceled (`action: 'cancel'`, charges only, not ones added by hand, which are deleted instead) sets `canceledOn` to today. `isLive()` (server) and `Fin.rcLive()` (page) leave canceled, dismissed and ended items out of totals, "Coming up", budgets' fixed-bill check, the bills report and Advice. If a canceled item's `lastDate` is more than 3 days after `canceledOn`, `view()` sets `chargedAgain`: an alert on Recurring and the Overview, counted in the badge. "Still have it" (`restore`) makes it confirmed again; "Got it" cancels it again from today. `restore` on a dismissed item makes it found again.
  - "Track as recurring" in a transaction's drawer (`action: 'track'`, `trackRecurring()`) pins that merchant (`pinned`, confirmed). It's always shown, as a `month` item built from whatever's there, even when nothing else would find it. "Not recurring" unpins it.
  - A scan runs after every sync, from the daily cron, and when the Recurring tab opens with a scan more than a day old.
  - `upcoming()` lists the next 30 days: each item's next dates (or a `month` bill's remaining parts), plus card and loan due dates (Plaid's `dueDate`, or a hand-kept debt's `dueDay`). A loan's due date is skipped when its payment already shows up as a recurring bill.
  - The summary's `monthTx` (this month and last, transfers left out) feeds the Overview's "This month" card, so the person filter works without another request.

  Budgets & goals (`api/_family/finance/plan.js`, `family/finance/plan.js`; two sections, `#budgets` and `#goals`, drawn by the same file; old `#plan` links go to Budgets):

  Credit (`api/_family/finance/credit.js`, `family/finance/credit.js`):

The answer is plain text; the page escapes it, then allows only `**bold**`, `- `/`1. ` lists and paragraphs, wrapping figures for hide-amounts.

  - **Scanning** (`family/documents/scanner.js`, `window.DocScanner.open({ title, start, mode })` → `{ pdf, pages, thumb, read }` or null; `mode` is the mode it opens in: `'page'` (the default), `'book'` or `'long'`; the old names `'auto'`/`'single'`/`'spread'` open in Book): a full-screen scanner, used for manuals and for receipts and documents on phones. Three modes, chosen by what's being added and switchable just above the shutter (Document / Book / Receipt): **Document** (`page`): every picture (or a single camera-app or picked photo) opens the corner check straight away (`openCrop(shot, 'check')`): the photo at once, then the found corners as soon as `shot.located` resolves (`cornersKnown()` in `shotPages()`, before a short yield so they show before the flattening), draggable, with Retake / Add a page / Save, so one page is shutter → Save. The camera keeps running underneath (`view()` only stops the outline), so Add a page is instant. A document's page is one page unless the check says "Two pages". **Book** (`book`, for manuals): the camera stays up page after page, a wide shot is split (auto), and everything is looked over at the end. Hands-free is offered only here (`autoShoot()`). **Receipt** (`long`): below. "Camera app" sits in the top bar. A live `getUserMedia` camera with a shutter (needs `camera=(self)`, see Security headers), or the phone's camera app / photo library as the fallback. The camera is asked for `width`/`height` ideal 4096 × 4096 (a square, so the highest mode wins whether the browser counts the phone as upright or sideways) and continuous focus where supported. The shutter watches the next ~0.5 s of frames and keeps the sharpest (variance of the Laplacian on a 320px patch at full size, in the page's middle), then flashes. Each shot is worked on at up to 4096px. Finding the page (`detect()`): OpenCV.js candidates from Canny (20/60, and again at 40/120: strong edges only, so wood grain can't join the page's outline to the table, which left a two-tone page, white above blue, closing up as one half or the other) and Otsu contours (`RETR_LIST`, convex hull → 4 corners), each one checked by `pageShaped()` (convex, corners 40–140°, 4–96% of the frame, at most one side along the frame edge) and `edgeSupport()` (a real edge under each side: Sobel gradient across the side, hits lining up in a straight line; three sides ≥ 0.5, mean ≥ 0.6), and weak-edged or small shapes must look like paper inside (`paperShare()`). There's no bounding-box fallback: no good candidate means no outline and the whole photo. Scored by area × edge strength, preferring the middle and wherever the page was a moment ago. A shot uses the live outline it was taken with (`hint`), fine-tuned by a search of the photo at 800px (then 480px) only if that lands near it. The live outline looks every 175ms at 360px, glides to each find on every frame (`glide()`), needs a far-away find twice in a row before jumping there and fades out after three misses (`follow()`). The flattening is one cubic `warpPerspective` straight to the final size (`pageScale()`: pages capped at 2400px, a smaller page enlarged towards 1700px, at most 2.5×), plus an unsharp mask; "Two pages (open book)" in the corners view, or Book mode's guess (a found page 1.2× wider than tall), splits it into two pages. Pages are then tidied by the filter, which cycles Color → Black & white → Original (applies to every page taken). Color and Black & white first get `clean()`: the light on the page is estimated from bare paper only (pixels near their local brightest and above 45% of the best-lit paper, on a 640px copy), filled in under text and pictures by normalized convolution (two Gaussian scales), and every pixel is brightened by `PAPER / light`, which evens out hand and phone shadows without haloing pictures; the paper's colour sets a white balance, applied when it's a warm (lamp) cast under 1.8× or any other tint under 1.06× (so pale pink or blue cards keep their colour). Then Color gets `levels()`, Black & white an adaptive threshold; Original is left as the camera saw it. Saved as JPEG 0.88 (0.85 B&W). Which way up: `lineTurn()` compares the stripiness of row and column ink profiles to spot sideways text (a quarter turn clockwise); then if the text reader's confidence is under 60 (`upright()` in `open()`), a 1100px copy is read the other way up (and both sideways ways under 40), and a clearly better reading (+15, ≥ 50) turns the page. Turns are kept per page on the shot (`shot.turns`, `shot.checked`), so turning by hand survives a filter change. **Receipt** mode (`mode: 'long'`): each shutter press (or camera-app photo; photos picked together) is a part, shown in a bar with Undo and Finish receipt; leaving the mode or the camera finishes it. The page finder's `long` flag allows a part to run off both the top and bottom. Parts are flattened to one width (a narrow receipt grows towards 1000px, capped 1400) and `stitch()`ed: ORB features (2000, ratio test) between the bottom of one part and the top of the next, a similarity transform by RANSAC (in JS, since this OpenCV.js has no `estimateAffinePartial2D`), checked for sane zoom/turn/offset; failing that a template match of the next part's top band; failing that it's stacked underneath with a toast. Seams go along the blankest row in the middle of each overlap (`quietRow()`), and the result stays under 14M pixels. Receipt pages have no "Fix the edges", and `readCopies()` sends the details reader a long page's top and bottom rather than one tiny whole. **Hands-free** (Book mode's top-bar switch, remembered in localStorage `sc-handsfree`): `watchStill()` takes the picture once the outline has moved under 1.5% and the frame's 40×30 grey signature under 5 for 0.9 s, but only after something changed since the last picture (outline lost, motion over 12, or the view's signature 16 away from the last shot's), so each page is taken once; a ring round the shutter (`--p`) fills while it waits. The screen is kept awake (Wake Lock) while the camera is up. Tesseract.js (v5, English `best_int`, on the device) reads each page's lines in the background; the PDF (pdf-lib) puts each page's JPEG on a 612pt-wide page, as tall as the page is, with the lines laid over it as invisible text (text render mode 3, `Tz` squeezed to the line's width; Helvetica, so non-Western characters become "?"). Review (Done, or the thumbnail by the shutter) lets you reorder, turn, remove, fix the corners (`openCrop(shot, 'fix')`, Cancel / Done: drag them; one page or two) and switch filter (only there: the camera has no filter button). The cover photo from step 1 comes in as page 1, never split.

## Frontend conventions

- **Grid columns**: use `minmax(0, 1fr)`, not a bare `1fr`, for any column holding user content. A bare `1fr` grows to fit its widest unbreakable word (like a long link in a recipe's notes), which pushes that section past the screen edge on phones. Prose also gets `overflow-wrap` so links wrap.
- **Touch screens**: the hub's `@media (pointer: coarse)` block (end of `hub.css`) sets text boxes to 16px, so iOS doesn't zoom in when one is tapped, and enlarges chips and small buttons to finger size. Keep new inputs and small controls covered by it. `styles.css` does the same for the Blog dropdown chevron.
- **Theme**: `data-theme="light|dark"` on `<html>`, choice persisted in `localStorage` under `lb-theme`. Default is light (system preference intentionally ignored). A one-line inline `<script>` at the top of every page's `<head>` (including `_src/post-template.html`) applies the saved theme before first paint so dark-mode users don't get a light flash — keep it in any new page. `main.js` also keeps `<meta name="theme-color">` in sync with the theme. All theme colors are CSS custom properties on `:root, [data-theme="light"]` and `[data-theme="dark"]` in `css/styles.css`; the accent green is `--accent`.
- **Animations**: `.reveal` class on any element triggers a GSAP fade-in on scroll (falls back to IntersectionObserver if GSAP fails to load, and to plain visibility under `prefers-reduced-motion`). GSAP + ScrollTrigger are loaded from cdnjs in each HTML file, with `defer` (as is `main.js`, which relies on that ordering).
- **Nav active state**: `main.js` compares bare page names (`about.html` → `about`) so it matches both locally and on Vercel's clean URLs (`/about`); anything under `/posts/` or `/classes/` highlights Blog. Post pages live at `posts/*.html`, so their nav links use `../index.html` etc.
- **Canonical URLs**: every page has `<link rel="canonical">` and `og:url` pointing at the clean URL (`https://www.loganbrandall.com/about`, `/posts/<slug>`).

## Site infrastructure

- **`404.html`** at the repo root is auto-served by Vercel for any not-found route. Styled to match the rest of the site (nav + footer included so users don't dead-end).
- **`apple-touch-icon.png`** (180×180, a photo of Logan and Marisa) at the repo root is the iPhone home-screen icon for every page. iOS picks it up from the root without a `<link>` tag.
- **Security headers**: `vercel.json` `headers` sends `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, a `Referrer-Policy` and a `Permissions-Policy` on every path. The Permissions-Policy turns the camera off everywhere except `/family/documents*` (`camera=(self)`, for the manual scanner), so it's two rules split by a negative-lookahead `source`; `.claude/serve.js` doesn't send these headers. There's no site-wide Content-Security-Policy yet (inline theme scripts, cdnjs, Google sign-in, Plaid and the CMS would each need allowing); only the public recipe page has one.
- **`robots.txt`** is hand-written and references the sitemap. No reason to change unless you want to block crawlers.
- **`sitemap.xml`** is regenerated by `build.js` on every build — don't hand-edit it, your changes will be overwritten.

Anywhere content was intentionally left blank for Logan to fill in, the literal word `Placeholder` is used (vs. fake bio copy), with a `TODO(Logan)` HTML comment nearby. Search the repo for either to find every spot that still needs real content (currently none).

## Things that bite

- The `injectBetween` markers in `index.html` / `blog.html` / every page's `<head>` are required — losing them silently breaks the build's output without an error. The full marker set: `POSTS_START`/`POSTS_END` (blog.html), `RECENT_POSTS_START`/`RECENT_POSTS_END` (index.html), `OG_IMAGE_START`/`OG_IMAGE_END` (every page's `<head>`), `BLOG_MENU_START`/`BLOG_MENU_END` (every page's nav), and `# POST_TO_TYPES_START`/`# POST_TO_TYPES_END` (`family/manage/config.yml`).
- All three homepage stats are rewritten by `build.js` via their `data-stat` attributes (projects shipped = number of `<article class="proj …">` cards in `projects.html`; blog posts and academic posts from `_posts/`) — keep the `data-stat="…" data-count="…"` attribute order, since `setStat()` matches it with a regex. Don't hand-edit those numbers.
- `SITE_URL` in `build.js` is hardcoded to `https://www.loganbrandall.com`. If the domain ever changes, update it there or social-share previews will point at the old URL.
- The hero photo's height is pinned via CSS `clamp()` (`clamp(540px, 72vh, 780px)` on desktop, `clamp(360px, 50vh, 500px)` under 900px wide, `clamp(260px, 36vh, 380px)` under 520px so the headline and buttons fit on a phone's first screen) for the cutout variant. The previous viewport-based `max-height: 82vh` caused the image to render at wildly different sizes on different laptops; don't revert it.
- `.md` files in `_posts/` only become live HTML after `npm run build` runs (Vercel runs it on every deploy). Posts created through the CMS land on GitHub as markdown only, so the committed `posts/*.html`, `blog.html` list and homepage stats lag behind until someone builds locally — the live site is fine either way.
- `SETUP.md` references a Cloudflare Worker for Decap auth; the live setup uses `api/auth.js` + `api/callback.js` instead. Don't follow SETUP.md verbatim for the auth piece.
